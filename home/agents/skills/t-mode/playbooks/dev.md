# Development

Applies after common intake selects development. Assigned workers follow their
brief rather than running intake. Design in this playbook means technical design;
a visual input alone does not reserve an additional review vendor.

1. Identify observable task properties: specification determinacy, construction
   difficulty/volume, error detectability, consequences and repair locality,
   dependencies/context, and waiting tolerance. Do not score everything or ask
   the user to classify the task.
2. Read [development workflows](../references/dev-workflows.md). Apply its route
   and evidence rules; do not invent a fresh cost model for each task. If a
   decisive technical property is unknown, obtain a bounded assessment rather
   than guessing or stalling.
3. Read [development models](../references/dev-models.md) when assigning roles.
   Select author and evaluator separately, preserving independence and known
   quota preferences. Follow the common brief and state rules.
4. Assign every required check to a role and target artifact before dispatch.
   A requirement stated only in reasoning is not an assignment. Workers may
   request checks, not remove required ones.
5. Run evaluation, repair and confirmation under the workflow rules. Report the
   evidence and remaining gaps; author self-tests or a done claim cannot replace
   a required independent verdict. Explicitly include evaluator confirmation of
   repairs at the new artifact in every independent-review route.

For sustained dependent deliverables, use the workflow's Poteto handoff:
resolve and include the installed entrypoint path, prior results/open work,
permissions, and coordination authority. A generic coordinator label is not
a substitute for that workflow.
